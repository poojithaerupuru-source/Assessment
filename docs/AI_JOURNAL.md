# AI Working Journal

I used an AI coding assistant (Claude, in Claude Code) as my main working interface for this assessment. This journal records what I asked for, what it produced, and whether I accepted it, challenged it or overrode it, with my reasoning. Entries are roughly in the order things happened.

My general rule throughout: the AI drafts, I decide. Anything it claimed from reading code I treated as a lead until it was proven by a test, a request or a log. I also kept Git in my own hands; the AI never committed or pushed anything.

---

## 1. Understanding the brief and getting the stack running

**Prompt:** Go through the assessment document and the app zip, and tell me in small steps what needs to be done. I already have Docker Desktop, a JDK, Maven, Git and Node installed.

**What the AI did:** Read both, gave me a phased plan (set up, run the app, assess, test, document, walkthrough), and pointed out early that the brief describes an Angular app with no tests, while the code is Next.js/React and already ships with some unit tests.

**Decision: accepted.** I checked the mismatch myself in the code and noted it in the strategy doc.

**Prompt:** My Java is 25 and `mvn` isn't found. Will that cause problems?

**What the AI did:** Checked the poms (they target Java 21), warned that the old JaCoCo plugin is likely to fail on JDK 25, found the Maven wrapper's `.mvn` folder missing, and told me to install JDK 21 and Maven.

**Decision: accepted**, and logged the missing wrapper as BUG-02.

**Prompt:** After logging in, the app shows "Build error", even after reopening it.

**What the AI did:** Read the UI container logs, found the generated API client was missing (git-ignored and never generated by the Dockerfile), generated it, rebuilt the UI container, and logged in to check the page loaded.

**Decision: accepted.** This became BUG-01: a clean checkout of the app doesn't run.

## 2. Risk assessment

**Prompt:** How do I read the source code and work out where the high-risk areas are? Then: create the strategy file with that risk table.

**What the AI did:** Suggested tracing three flows end to end (submit a claim, change a status, live update) and judging each area by damage, complexity and whether it sits between two systems. It then read the security, claims, Kafka and WebSocket code and produced eight ranked risks with file and line references.

**Decision: accepted as leads, not findings.** Each risk stayed marked "lead" until something proved it. Later I **overrode the format**: I asked for the strategy doc to be rewritten as plain prose without tables or diagrams, so it reads like my own working notes.

## 3. Choosing the framework and building the structure

**Prompt:** I want a BDD framework in this repo: feature files, page objects, step definitions and utils, Playwright for the browser, run with npm only, in its own subfolder. Is that a good idea?

**What the AI did:** Agreed for the end-to-end and API layer, recommended playwright-bdd over cucumber-js (it keeps Playwright's own runner, reports, traces and fixtures), and warned that the unit and component tests the brief requires shouldn't be forced into Gherkin.

**Decision: accepted.** It fits how I like to work, and I can explain the choice.

**Prompt:** I gave it the user flows to cover and asked for a basic folder structure with features, Background steps, step definitions and page object methods, using **placeholder locators that I would replace**, written in JavaScript rather than TypeScript.

**What the AI did:** Built `qa-tests/` with three feature files, page objects with clearly marked `TODO-` locators, a fixtures file, step definitions and utils (routes, test users, a claim data builder), and checked that every step was bound.

**Decision: accepted the structure.** The placeholder locators were then replaced with real ones taken from the running app: I had the assistant inspect the live pages' accessibility tree, and I reviewed each locator (role and label based, scoped to the main content where the header had duplicate buttons). Running against the real app surfaced several test issues it then fixed: descriptions truncated in the claims table, the slow dev-mode UI, and an account lock (see entry 5).

## 4. Credentials

**What happened:** The first version of the test users file had the demo passwords as hard-coded fallbacks.

**Decision: challenged and overrode.** I asked why passwords were sitting in the file and whether they could be GitHub secrets. They now come only from environment variables: a git-ignored `.env` locally, and GitHub Actions secrets in CI. The AI also pointed out that GitHub secrets only work inside Actions, so the `.env` file is still needed locally, which I hadn't realised.

## 5. A flaky test that became a real bug (BUG-03)

**What happened:** Logged-in scenarios failed now and then, with correct passwords rejected. The AI dug into Keycloak's logs instead of adding retries, found that failed logins in one test were locking the shared claimant account, and switched the negative login test to an unregistered email. Then it found something bigger: two logins for the same user at the same instant get one 200 and one 401. It reproduced that with `curl` (3 out of 3 pairs).

**Decision: accepted the finding, then challenged the impact claim.** The strategy doc said this would hit "anyone who double-clicks Log In". I asked whether it had actually tried that by hand. It hadn't, and when it checked, the Log In button disables itself during login, so a double-click almost certainly can't trigger it. The doc now says BUG-03 is confirmed at the API level and mainly affects automated clients sharing an account. For me this was the most important lesson of the exercise: only claim what you've proven.

**Prompt (follow-up):** How do I reproduce BUG-04 (a locked account shown as "Invalid email or password")?

**What the AI did:** Worked out that two failed logins less than a second apart lock an account for 60 seconds, locked our own test user that way, then logged in through the UI with the correct password and got "Invalid email or password". It unlocked the user afterwards.

**Decision: accepted.** The reproduction steps are now in the strategy doc.

## 6. Signup is broken (BUG-05, BUG-06)

**Prompt:** Signing up from the app fails with "Signup failed". If it's an app issue, let's cover it in the suite and show it as a bug.

**What the AI did:** Reproduced a 500 through the API, then traced the cause: the BFF logs in to Keycloak's admin API with password `admin`, but Keycloak runs with `Admin123!`. It added a signup scenario tagged `@bug @fail` (an expected failure, so the build stays green but the bug stays visible), and also noticed the signup page reports every server error as "Network error".

**Decision: accepted.** It also suggested a one-line config fix, and I deliberately didn't apply it: my job here is to find and report bugs, not change the app.

**Prompt (later):** Do we have a contract test for BUG-06? Is it worth one?

**What the AI did:** Said no contract tests exist, explained that BUG-06 is UI logic so a component test would suit it better, and that contract testing would be most valuable for BUG-05 and BUG-07.

**Decision: overrode.** I decided it wasn't needed, because the existing signup UI scenario already exercises that path and the message issue is low impact. I noted that BUG-06 is backed by a manual check and the code reference, not by its own test.

## 7. API tests and data isolation (BUG-07)

**Prompt:** Add API features for 401 and 403. I also want to check that claimant 1's claims aren't visible to claimant 2, but we can't, because signup is broken.

**What the AI did:** Probed the real API first to see actual status codes, then built an API client with one cookie session per role and automatic CSRF tokens. As a workaround for signup, it creates the second claimant directly through Keycloak's admin API. It wrote features for 401, 403, CSRF, login and isolation. It also included a control case: a claimant changing a status gets 403 even **with** a valid CSRF token, while the admin's identical request gets 200. That proves the 403 comes from the role check and not from a missing token. The probe showed isolation holds, but the BFF returns 500 where its own contract promises 403, 404 or 400 (BUG-07).

**Decision: accepted, after a correction.** Its first "no data leaked" check looked for the claim ID in the response and failed, because the 500 error body repeats the URL, which contains the ID. The check now looks for the claim's private description instead. Not trusting a test until you understand why it fails was a useful reminder.

## 8. Quoting values in feature files

**What happened:** I edited a feature to put `"GET"` in quotes. Four tests broke with "Method must be a valid HTTP token". The step used `{word}`, which captured the quote marks too.

**Prompt:** Why is the status written as `{int}` with an unquoted 401? Why not take everything as strings?

**What the AI did:** Explained `{string}`, `{int}` and `{word}`, switched the HTTP method to `{string}` with quotes in every feature (keeping my change), and kept `{int}` for status codes so the step receives a real number.

**Decision: accepted the explanation, kept my quoting change for methods.** Quote text, don't quote numbers.

---

## 9. Environment problems that looked like test failures

**What happened:** API tests started failing randomly with `ECONNRESET`. The AI showed that plain `curl` worked 100 out of 100 times while Playwright's reused connections were being reset by Docker Desktop's port forwarding on Windows. It now sends `Connection: close` on API requests.

**Decision: accepted.** The API suite went from 2–6 minutes with random failures to about 8 seconds with none.

**What happened:** VS Code showed every step as undefined. The AI found I had opened the folder one level too high, and had two competing Cucumber extensions installed. It added workspace settings for both.

**Decision: accepted.** I reopened the correct folder.

---

## 10. An intermittent failure that became a real bug (BUG-08)

**Prompt:** Check all the tests and tell me if anything more should be added.

**What the AI did:** While reviewing, the admin filter test failed once the API tests had created claims with other statuses. It checked that the API filter itself was correct, then found the UI keeps whichever response arrives last: a slow unfiltered load can overwrite a filtered list. It made the normal test wait properly, and added a `@bug @fail` scenario that delays the unfiltered response to reproduce the bug every time ("Expected 0 other-status rows, Received 9").

**Decision: accepted.** Turning an intermittent failure into a bug you can reproduce every time is one of the stories I'll tell in the walkthrough.

## What's covered now

The suite in `qa-tests/` has 27 scenarios across 7 feature files, all passing, with 4 of them being known bugs run as expected failures.

Through the UI: claimant and admin login land on the right pages, an unregistered user sees an error, signup (BUG-05, expected failure), a claimant submitting a claim through the wizard and seeing it listed as Submitted, the admin claims table, filtering by status, and the filter race (BUG-08, expected failure).

Through the API: anonymous calls to four protected endpoints get 401, a malformed token gets 401, a claimant gets 403 on three admin endpoints while the admin gets 200, a claimant can't change a status while an admin can, writes without a CSRF token are rejected, login returns the session cookie, unknown credentials get 401, a claim's owner can read it, another claimant can't see it in their list or read it by ID, and the two contract cases (403 and 404, BUG-07, expected failures).

## Where more testing is needed

Unit and component tests are the biggest gap, and the brief requires them. I'd start with JUnit tests for all 25 status transitions and the money limits (0, 0.01, 1,000,000, 1,000,000.01), and Vitest component tests for the claim wizard's validation and the admin status dropdown. The project's own existing unit tests also need running and fixing (the README says one is broken).

Live updates are untested. An end-to-end test with two browser windows would show whether a status change reaches the claimant without a refresh, and would settle the lead about event publishing being switched off.

At the API level, the claim validation rules (amount limits, future dates, description length) and the invalid status transition (BUG-07's third case) should get their own scenarios, and the signup API (BUG-05) could be covered there too.

On the UI side, page guards are missing: a logged-out user opening `/claims` should be sent to login, and a claimant opening `/admin/claims` should be kept out.

Contract checks against `bff-api.yml` would catch BUG-07-style problems automatically for every endpoint. A small k6 load test would hit BUG-03 straight away with shared users, which is worth showing. The timezone lead on the incident date also needs a test.
